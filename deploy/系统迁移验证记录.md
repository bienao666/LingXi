## 真实双项目演练

WSL Ubuntu 内两个完全隔离的 Compose 项目，分别使用独立 PostgreSQL、runtime／resources 具名卷、Core、worker、Web 及 Hindsight 1.1.0-slim。只共享专门生成的 QA 主密钥，数据库凭据各自随机；公共入口分别为 8081 和 8082。未复制正式 `.env`、所有者或真实聊天数据。

演练通过以下过程：

1. 初始化合成源所有者和空目标；源写入中文会话、记忆与删除记录、模型连接，以及通过真实 HTTP 上传并解析的 Markdown 附件。
2. 目标终端生成注册，源通过真实 HTTP 预览及明确确认建立计划；重复请求返回同一记录。
3. 源终端持久化停写、排空并冷备两库及资料卷，核验清单并生成加密交接证明；只恢复 Core／Web，源端保持冻结。
4. 整个归档在 WSL 受保护目录间复制。修改真实 PostgreSQL dump 的一个字节，预检在覆盖目标之前拒绝；恢复原件后通过。
5. 第一次真实导入暴露 ORM 模块经 `__main__` 与规范包名重复加载的问题。运行器改为规范导入后，恢复空目标并重新验证。
6. 在数据库、文件和隔离核验全部成功后注入故障，确认目标为 `target_pending`、应用保持停止、journal 与回退包保留。标准 `recover` 可回到原注册的空目标。
7. 另模拟导入提交后、journal 清理前进程丢失。`recover` 停止已恢复的 Core／Web，恢复初始目标；实际检查无业务行、无遗留附件文件，仍满足空目标预检，再次导入同一包成功。
8. 目标待激活时核对中文会话、有效记忆、已删除记忆不复活、附件实际内容与 SHA256；外部模型和插件保持禁用，旧登录撤销，目标仍暂停。
9. 显式激活后再次核对数据与授权。真实 HTTP 登录后可读取原中文会话，记录为已完成；不返回目标票据或模型明文密钥。
10. 重启源端 Core 后仍为 `source_frozen`，HTTP 业务读写返回 503，worker 领取检查为空；源端未解冻。这里只验证 QQ 入口门禁及恢复关闭逻辑，没有登录真实 QQ 或搬运真实 NapCat 登录。
