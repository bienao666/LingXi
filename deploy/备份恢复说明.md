# 备份恢复

本批实现服务器工作区冷备份、完整性核验、定时请求，以及同版本历史回退。Web 不接收恢复归档，不下载备份，不持有 Docker socket。跨服务器交接使用独立的[系统迁移流程](./系统迁移使用说明.md)；全损灾难恢复和独立商店备份仍待开发。

## 安装运行器

要求 Linux、Python 3 标准库、Docker CLI／Compose，以及访问当前项目容器的主机权限。默认项目名 `lingxi`，项目目录必须包含 `compose.yaml`。WSL 可用于联调，关闭 WSL 后运行器不会继续执行。

在服务器项目目录执行；备份目录使用 Linux 文件系统，不能直接使用权限不受控的 Windows 挂载目录：

```bash
sudo install -d -m 0700 /var/lib/lingxi/backups
sudo python3 deploy/backup.py serve --project-dir /opt/lingxi --backup-dir /var/lib/lingxi/backups
```

每 15 秒领取一条操作，`--once` 只领取一次。Web 显示最近 60 秒是否有运行器心跳。服务初次启动需要单所有者已初始化，数据库迁移到 `0015`。不能同时运行同一 Compose 项目的多个运行器，即使归档目录不同；按项目的主机文件锁和数据库状态共同防止重入，要求同一 Linux 操作账号。执行迁移前先停止常驻备份运行器。

如需服务器常驻，可按实际路径创建 systemd 服务，先手动验证运行器和备份目录：

```ini
[Unit]
Description=Lingxi workspace backup runner
After=docker.service
Requires=docker.service

[Service]
Type=simple
WorkingDirectory=/opt/lingxi
ExecStart=/usr/bin/python3 /opt/lingxi/deploy/backup.py serve --project-dir /opt/lingxi --backup-dir /var/lib/lingxi/backups
Restart=on-failure
RestartSec=15
UMask=0077
User=root

[Install]
WantedBy=multi-user.target
```

主机权限相当于 Docker 管理权限；运行器不应接受第三方任意参数或作为公开 HTTP 服务。本机交付默认不安装 systemd、不打开定时备份；运行器离线时 Web 请求保持排队，可明确取消。

## 备份范围和停写

“系统设置 → 备份恢复”可确认创建、核验、取消排队请求及配置定时间隔。默认关闭定时，间隔 1–168 小时，从保存时开始计算。离线后只补一次，不追赶全部遗漏周期。仅展示最近 100 次记录，不自动清理历史文件，应另外监控容量和保留策略。

冷备份先阻止新 HTTP 业务写入和 worker 调度，最多等待 60 秒让活动作业／语音结束；仍忙则失败。之后停止原来运行中的 Core、worker、Web、Hindsight 和已存在的 NapCat，数据库保持运行。备份生成后按依赖顺序恢复原运行组件；原本停止的组件不启动。此间浏览器会短暂断线。

| 文件 | 范围 |
|---|---|
| `main.dump` | PostgreSQL 业务数据库、配置、会话、任务与权威记忆 |
| `hindsight.dump` | Hindsight 数据库，索引为可重建的派生数据 |
| `runtime.tar` | 删除账本、上传附件等运行卷 |
| `resources.tar` | 已授权服务器资料卷 |
| `qq.tar`、`qq-config.tar` | 仅当已有 NapCat 容器存在时备份其资料及配置 |
| `manifest.json` | 格式、数据库版本、主密钥指纹、所有者、镜像信息、各文件字节数与 SHA256 |

不包含服务器 `.env` 和主密钥、独立插件商店、远程 S3、模型缓存。主密钥及服务环境须独立安全保管；缺失密钥不能解密历史连接配置。归档含个人资料、密码摘要和加密密钥，目录 0700、文件 0600；本批未实现归档加密或异地复制，不应直接上传公开存储。

`latest-safety.json` 保存最新安全状态，含认证摘要、加密 TOTP、权威记忆、联系偏好和删除记录；属于敏感文件，不能发布或作为诊断附件。备份和恢复期间禁止部署升级、移动镜像标签、手工改库或修改卷。运行器锁定本地 Core 镜像别名；应保留该镜像，不在操作未结束时执行镜像清理。

## 核验和历史回退

```bash
sudo python3 deploy/backup.py verify 备份编号 --project-dir /opt/lingxi --backup-dir /var/lib/lingxi/backups
sudo python3 deploy/backup.py restore 备份编号 --project-dir /opt/lingxi --backup-dir /var/lib/lingxi/backups
```

核验检查摘要、大小、归档范围、PostgreSQL 格式标记和文件路径，不证明业务质量，也不是数字签名或完整恢复演练。只恢复由受信任的本项目运行器生成的归档；拥有主机写权限的人也能改写摘要。数据库 dump 不应来自未知来源。

当前恢复要求原工作区仍可读取，且数据库 schema、主密钥和所有者一致，Core／worker／Web／Hindsight／数据库容器及命名卷仍存在。预检会验证本地固定的离线辅助镜像；镜像标签已移动时拒绝，需先核对并重建 Core。恢复期间不拉取镜像、不自动迁移历史数据库。

输入 `RESTORE 完整备份编号` 后停写、停止服务，重新保存当前安全状态，再自动生成一份回退备份，之后覆盖两库和同名卷文件。Hindsight 应用对象恢复给其普通数据库角色；扩展对象保留安装者归属。**文件恢复覆盖同名文件，不删除卷中后来新增的文件，不等于精确文件树回退。** 重复归档、非法路径、链接和设备节点会拒绝。

覆盖后保留当前密码／TOTP／恢复码消耗状态、当前权威记忆及纠正删除、当前联系拒绝和最新删除账本；使依赖结果失效，并创建新的安全索引／删除清理作业。撤销全部登录，关闭模型连接、QQ 渠道、插件和商店连接、主动联系和定时备份；撤销 QQ 身份绑定及插件权限。旧任务、提醒、语音与未确认的外部发送保持隔离，不自动重放；操作未知不改报成功。

恢复后 NapCat 保持停止，即便原来运行；不会为用户重新登录 QQ。逐项核对真实状态，再重新授权模型、渠道、插件和联系设置。worker 仅恢复原先的运行状态；原先未运行的 worker 需在核对后启动，处理安全重建作业。

## 中断处理

出现 `in-progress.json` 时禁止创建新备份，保留目录、最新安全状态和固定镜像，先在服务器终端运行：

```bash
sudo python3 deploy/backup.py recover --project-dir /opt/lingxi --backup-dir /var/lib/lingxi/backups
```

备份或尚未改库的准备阶段中断，可释放维护状态并恢复原组件。已进入覆盖阶段会要求输入 `ROLLBACK 自动回退编号`，恢复自动回退包并再次应用最新安全约束；原恢复记录为中断，不冒充成功。再次失败时继续停止服务，保留文件，由终端排查，不通过手工删除维护记录强行开放。

主机错误详情保存在目录中的 `runner-error.log`，权限 0600，最多保留最近一次错误末尾 32 KiB；可能含 SQL、路径或敏感信息，不通过 Web 展示或自动收进诊断。空间不足时可留下 `.partial`；排查后人工核对，不能把未完成目录作为成功备份。不要删除 `.runner.lock` 或仍活跃的临时文件绕过锁。
